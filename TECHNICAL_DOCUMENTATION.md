# Техническая документация: программный комплекс прогнозирования доходности OZON (MOEX)

## 1. Назначение и общая архитектура

### 1.1. Назначение

Программный комплекс реализует прикладной эконометрико-ML конвейер для прогнозирования **лог-доходностей** дневного ряда акций OZON на горизонтах \(h \in \{1, 5, 10\}\) торговых дней (настраивается через `HORIZONS` в `config.py`). Решаются две задачи:

- **Регрессия**: прогноз кумулятивной лог-доходности \(\sum_{k=1}^{h} r_{t+k}\).
- **Классификация направления**: знак этой суммы (ноль/единица).

Дополнительно для отчёта собираются **торговые метрики** простой long/short-стратегии по знаку прогноза, эконометрический baseline **ARIMA + GARCH** и опционально NLP-признаки тональности новостей.

### 1.2. Точка входа и оркестратор

- **`main.py`** — CLI: аргументы `--data`, `--out`, `--smoke`. Режим `--smoke` обрабатывает первые 50 строк, прогоняет загрузку → валидацию → индикаторы → построение признаков и таргетов и не запускает ML/ARIMA — служит для проверки окружения и формата данных.
- **`pipeline.run_experiment(cfg, data_path, out_dir, *, use_news_features=None)`** — единый сценарий одного прогона: `load_data` → `validate_data` → `build_features_dataframe` → `run_eda` → `export_eda_stats` → `run_hybrid_arima_garch` → `run_ml`. Возвращает словарь `{data, arima_garch, ml, out_dir, use_news_features}` и сохраняет артефакты в `out_dir`. Опциональный аргумент `use_news_features` принудительно включает/выключает новостные признаки независимо от `cfg`.
- **`pipeline.run_ab_comparison(cfg, data_path, out_dir)`** — оркестратор A/B: запускает `run_experiment` дважды (без новостей и с новостями) с одинаковыми сидами и сплитами, формирует Δ-таблицы метрик и сводный отчёт (см. §2.17).
- **`config.py`** — единый словарь `CFG` со всеми параметрами; в коде `cfg.get(...)` обеспечивает обратную совместимость и значения по умолчанию.

### 1.4. Схема формирования обучающего датасета

В обоих режимах A/B (с новостями / без) используется **один и тот же конвейер
формирования датасета**; единственное расхождение — наличие 5 новостных
признаков в матрице `X` (см. §2.17). Это гарантирует одинаковые сплиты,
одинаковые отбракованные строки и сравнимость результатов.

```mermaid
flowchart TD
    A[CSV котировок<br/>OZON_combined.csv] --> B[data.loader.load_data<br/>OHLCV + DatetimeIndex]
    B --> V[data.validator.validate_data<br/>дубликаты, ffill, MAD-z диагностика]
    V --> R[features.returns.compute_log_returns<br/>log_ret = ln(C_t/C_{t-1})]
    R --> I[features.indicators.compute_indicators<br/>TA + HAR-RV + OBV_z + календарь + лаги]

    N0[CSV новостей<br/>data/news.csv] -.optional.-> N1[news.io.load_news_csv<br/>+ news.preprocess.clean_news_text]
    N1 -.-> N2[news.ozon_filter.maybe_filter_ozon_after_parse<br/>оставить публикации про Ozon]
    N2 -.-> N3[news.sentiment.ensure_sentiment_column<br/>RuBERT → s ∈ -1..+1]
    N3 -.-> N4[news.aggregate.daily_sentiment_features<br/>day-aggregate по торговому индексу:<br/>sentiment_score, news_count, has_news,<br/>sentiment_trend_3, sentiment_volatility]

    I --> M[news.merge.attach_news_sentiment_features<br/>USE_NEWS_FEATURES?]
    N4 -.-> M

    M -->|True: + 5 news cols| F1[df_feat: TA + News]
    M -->|False| F2[df_feat: только TA]

    F1 --> FB[features.builder.FeatureBuilder<br/>build_features + build_targets]
    F2 --> FB
    FB --> X[X: матрица признаков<br/>tg: reg_h, clf_h]

    X --> WF[models.walk_forward<br/>purged WF + RobustScaler train→test]
    WF --> METR_REG[regression_metrics<br/>MAE/RMSE/MAPE/R²/IC/MDA]
    WF --> METR_CLF[classification_metrics<br/>Accuracy/F1/AUC]

    R --> AG[models.walk_forward.<br/>rolling_forecast_hybrid_arima_garch]
    AG --> ARIMA_REG[ARIMA(-GARCH) regression<br/>arima_horizons_metrics.csv]
    AG --> ARIMA_CLF[sign(mu_forecast) → classification<br/>arima_horizons_clf_metrics.csv]

    METR_REG --> CMP[evaluation.comparison<br/>build_*_comparison + winners_table]
    METR_CLF --> CMP
    ARIMA_REG --> CMP
    ARIMA_CLF --> CMP
    CMP --> AB[ab_comparison_summary.csv<br/>ab_winners_*.csv + ab_meta.json]
```

**Используется ли единый датасет для всех моделей?** Да:

- ML-регрессия и ML-классификация используют **одну и ту же** матрицу `X` и
  один и тот же индекс, целевые ряды отличаются только определением
  (`reg_h` — кумулятивная сумма, `clf_h = 1{reg_h > 0}`).
- Стекинг работает на той же `X` (только hold-out: последние `TEST_FRACTION` ряда).
- ARIMA(-GARCH) использует **подмножество** этого датасета — только колонку
  `df["log_ret"]`, потому что эконометрическая модель работает с одномерным
  временным рядом. Это сознательный выбор: новости не влияют на ARIMA-блок,
  что превращает его в стабильную контрольную точку при A/B.

В A/B-сравнении эта схема исполняется дважды — с одинаковыми сидами и
одинаковыми WF-сплитами, но с разным набором колонок `X` (с news-колонками и
без них). Все остальные шаги — идентичны.

### 1.5. Поток данных от входа до результата

1. **Источник** — CSV котировок (`FILE_PATH` или `--data`); опционально CSV новостей (`NEWS_CSV_PATH`).
2. **Loader (`data/loader.py`)** → `pd.DataFrame` OHLCV с `DatetimeIndex` (UTC-naive, нормализован к датам).
3. **Validator (`data/validator.py`)** → очищенный `df`: дубликаты индекса, ffill цен, медианная импутация объёма, диагностика робастных выбросов лог-доходности (без удаления).
4. **`pipeline.build_features_dataframe`** → `df_feat`:
   - добавляет `log_ret`,
   - вызывает `compute_indicators` (ТА + HAR-RV + OBV-z + календарь + лаги),
   - при `USE_NEWS_SENTIMENT=True` вызывает `attach_news_sentiment_features` и добавляет 5 новостных колонок.
5. **EDA**: `run_eda` (графики) и `export_eda_stats` (ADF, сезонность, корреляции, классы тональности).
6. **ARIMA-GARCH**: `run_hybrid_arima_garch` — rolling-прогноз `log_ret`, выбор лучшего \(h\), артефакты + график.
7. **ML**: `run_ml` — `FeatureBuilder` собирает `X` и `tg`, выравнивает; для каждого \(h\) запускается `walk_forward_train_eval` (Ridge, RF, LGB regressor + RF, LGB classifier), считаются торговые метрики, baseline Naive(0) и Buy&Hold; формируется hold-out для стекинга.
8. **Ablation новостей** (опционально): второй прогон ML без новостных признаков и сравнительный CSV.
9. **Артефакты**: CSV метрик, JSON сводок (`best_models_wf.json`, `arima_best_horizon.json`), PNG-графики.

### 1.6. Связь компонентов

`pipeline` — фасад: импортирует объекты из `data`, `features`, `news`, `models`, `evaluation`, `visualization`. Внутри ML-блока единственная общая «склейка» — `_prepare_targets_and_features`, дающая выровненные `X` и `tg`. ARIMA-GARCH работает независимо от ML и потребляет только `log_ret` и метаданные `cfg`.

## 2. Pipeline по шагам

### 2.1. Загрузка данных (`data/loader.py`)

**Метод.** `pandas.read_csv` с перебором разделителей `,`, `;`, `\t`. Колонки приводятся к верхнему регистру и очищаются от пробелов/`<`/`>`. Колонка `DATE` парсится через `pd.to_datetime`; индекс сортируется и устанавливается на `DATE`. Числовые колонки `OPEN/HIGH/LOW/CLOSE/VOL` приводятся через `pd.to_numeric(errors="coerce")`. Строки с NaN по OHLC удаляются.

**Почему так.** Формат CSV у MOEX/Excel непредсказуем (разделители, регистр, угловые скобки). Перебор разделителей и нормализация имён исключают ручное редактирование файла. `to_numeric(errors="coerce")` устойчив к строкам-заглушкам и нечисловым артефактам экспорта.

**Альтернативы и их минусы.** Жёстко заданный `sep=","` ломается при экспортах с `;`. `pd.read_csv(... parse_dates=...)` без явной обработки упадёт на нестандартных строках; в текущей версии используется отдельный шаг с `to_datetime` в `try/except`, дающий понятное сообщение об ошибке.

**Создаётся.** `df: pd.DataFrame` с колонками OPEN/HIGH/LOW/CLOSE/VOL, индекс — `DatetimeIndex`. Передаётся в `validate_data`.

Дополнительно `load_trading_dates(filepath)` возвращает множество `set[date]` календаря котировок — используется в `news/filters.py` для ограничения новостей днями торговли.

### 2.2. Валидация и предварительная очистка (`data/validator.py`)

**Шаги.**

1. **Дубликаты индекса.** `keep="last"`: остаётся последняя запись на дату.
2. **Сортировка по индексу.**
3. **Календарная диагностика.** `pd.bdate_range(min, max)` сравнивается с фактическим индексом; пропуски только **логируются**, ряд не достраивается синтетически.
4. **Пропуски в ценах.** `OPEN/HIGH/LOW/CLOSE` заполняются **forward fill** (последнее наблюдение).
   **Почему ffill, а не интерполяция.** Для биржевых котировок «нарисованная» интерполяция между последним и следующим торгом создаёт несуществующие значения; ffill сохраняет последнюю реальную цену, что соответствует логике рынка «нет торгов — последняя сделка».
5. **Объём.** `VOL.fillna(rolling(20).median())` — медиана за 20 дней. Медиана робастна к экстремальным дням «хайп»-объёма; среднее в этой роли смещалось бы в сторону аномальных всплесков.
6. **Выбросы доходности.** Считается `log_ret`, затем робастный z-score через **медиану и MAD** (`(x − median) / (1.4826·MAD)`). Превышение `OUTLIER_ZSCORE` (по умолчанию 3.5) **только логируется** — экстремальные дни OZON 2022–2024 рассматриваются как реальные.

**Почему MAD-z, а не классический z-score / IQR / 3σ.** Распределение лог-доходностей OZON сильно отличается от нормального (тяжёлые хвосты, эксцесс ≫ 3). MAD-оценка масштаба устойчива к выбросам и не «раздувается» от единичного экстремального дня, в отличие от стандартного отклонения. IQR/межквартильный — близкая по сути альтернатива; MAD выбран как симметричный относительно медианы и стандартный для робастной статистики финансовых рядов.

**Создаётся.** Очищенная копия `df`; передаётся в `build_features_dataframe`.

### 2.3. Лог-доходность (`features/returns.py`)

**Формула.** \(r_t = \ln(C_t / C_{t-1})\). Первое значение — `NaN` (отсутствует предыдущее наблюдение).

**Почему лог-доходность, а не простая (`pct_change`).**
- **Аддитивность по времени.** Сумма лог-доходностей даёт лог-доходность за весь период — без этого свойства нельзя корректно строить таргет «кумулятивная доходность за \(h\) дней».
- **Симметрия.** Доходность +5% и −5% при простой формуле не компенсируются; в логах симметричны.
- **Стационарность.** Логи цен близки к интегрированному ряду, а лог-доходности — к стационарному (это эмпирически проверяется ADF в `export_eda_stats`).

### 2.4. Признаки технического анализа и календаря (`features/indicators.py`)

Функция `compute_indicators(df, cfg)` добавляет 35+ признаков. Группы:

#### 2.4.1. Лаги лог-доходности

```python
n_lags = max(0, int(cfg.get("N_LAGS", 0)))
for k in range(1, n_lags + 1):
    out[f"log_ret_lag{k}"] = log_ret.shift(int(k))
```

`N_LAGS=10` по умолчанию: создаются `log_ret_lag1..log_ret_lag10`. **Почему.** Авторегрессионная структура — типовой источник предиктивности коротких рядов; лаги дают линейным и древовидным моделям прямой доступ к локальной автокорреляции без необходимости явно оценивать ARIMA.

#### 2.4.2. Скользящие средние и относительные положения

- `sma{p}` для `SMA_PERIODS=[20, 50, 200]` (классические границы краткосрочного, среднего, долгосрочного тренда).
- `price_vs_sma20` = \((C - SMA_{20}) / SMA_{20}\) — масштаб-инвариантное отклонение цены от тренда (модели не получают «сырую» цену в рублях, склонную к нестационарности).

#### 2.4.3. Моментум и осцилляторы

- `RSI14` (`RSI_PERIOD=14`).
- `STOCHK` — Stochastic %K(14, 3).
- `BBpctb`, `BBwidth` — Bollinger Bands.
- `MACDnorm` = `macd_diff() / close` — нормированная разность MACD.

**Почему именно эти.** Это базовый набор технического анализа, отражающий моментум (RSI, Stoch), нелинейные каналы цены (BB), сходимость скользящих средних (MACD). Нормировка на цену делает признаки масштаб-инвариантными при тренде долгосрочной цены.

#### 2.4.4. Волатильность

- `ATRnorm = ATR(14) / close`.
- `vol_std5`, `vol_std20` — реализованная волатильность (std лог-доходности).
- **HAR-RV (Heterogeneous AutoRegressive Realized Variance)** в упрощённом виде: `har_d` = \(r_{t-1}^2\), `har_w` = среднее квадратов за 5 дней, `har_m` — за 22 дня. Стандартная модель Corsi (2009): волатильность сегодня объясняется суммой компонент дневного, недельного и месячного горизонтов.
- **`rv_park5`** — оценка Parkinson по диапазону high-low: \(\frac{(\ln H_t/L_t)^2}{4\ln 2}\), усреднённая за 5 дней. Преимущество перед close-to-close: использует внутридневные движения.
- Лаги волатильности: `ret_sq_lag1`, `ret_abs_ma5`, `ret_abs_ma20`, `sign_lag1`.

**Почему такой набор.** Финансовые модели (GARCH, HAR) показали, что волатильность сильно автокоррелирована и кластеризована; явные признаки разной агрегации (день/неделя/месяц) дают деревьям и Ridge доступ к этой структуре без необходимости сложной авторегрессии.

#### 2.4.5. Объём (`OBV_z`)

```python
obv = ta.volume.on_balance_volume(close, vol)
obv_norm_w = int(cfg.get("OBV_NORM_WINDOW", cfg.get("OBV_WINDOW", 20)))
obv_norm_w = max(2, obv_norm_w)
obv_ma = obv.rolling(obv_norm_w).mean()
obv_std = obv.rolling(obv_norm_w).std()
out["OBV_z"] = (obv - obv_ma) / (obv_std + 1e-8)
```

OBV — кумулятивный индикатор объёма со знаком; «сырой» OBV монотонно растёт и нестационарен. Здесь применяется **rolling z-score** по окну `OBV_NORM_WINDOW` (по умолчанию 50): вычитается локальное среднее и нормируется на локальный std. Это даёт стационарный признак «насколько текущий OBV отклонился от своего тренда за последние ≈ 2,5 месяца торгов». Fallback на `OBV_WINDOW=20` сохраняет совместимость с прошлыми экспериментами; минимальное окно 2 предотвращает деление на 0.

**Почему окно 50.** На дневных данных это охватывает ~10 рабочих недель — достаточно для устойчивой оценки локального масштаба и одновременно позволяет признаку реагировать на смену режима в течение квартала.

#### 2.4.6. Календарные признаки

- **Циклическое кодирование**: `month_sin/cos`, `dow_sin/cos`. Преимущество перед one-hot: декабрь и январь близки в евклидовом пространстве, а one-hot объявляет их максимально разными. Линейные модели (Ridge) при one-hot месяцев получают 12 коэффициентов; в sin/cos — всего 2 признака с непрерывной геометрией.
- **Бинарные индикаторы**: `is_month_end`, `is_quarter_end`, `is_friday`, `is_march`, `is_july`, `is_oct`. Это ручные «эмпирические» эффекты, выявленные на EDA сезонности.
- **Структурный режим**: `in_crisis = 1{2022-02-24 ≤ t ≤ 2022-12-31}`. Используется не только как признак, но и как индикатор для уменьшения веса наблюдений (см. 2.10.3).

**Что НЕ создаётся.** В коде нет one-hot/LabelEncoder. Все «категориальные» эффекты сразу закодированы числами (sin/cos и бинарными индикаторами), поэтому отдельный шаг кодирования не нужен.

**Создаётся.** Расширенный `DataFrame` `out` (входной OHLCV + индикаторы + лаги + календарь). Передаётся в `attach_news_sentiment_features` и затем в `FeatureBuilder`.

### 2.5. Новостные признаки (`news/*`, опционально)

Включается флагом `USE_NEWS_SENTIMENT=True` и наличием `NEWS_CSV_PATH`.

#### 2.5.1. Загрузка и очистка (`news/io.py`, `news/preprocess.py`)

- Авто-выбор колонки даты по алиасам (`date`, `published`, …) и текста (`text`, `body`, …). Можно явно указать через `NEWS_DATE_COL`, `NEWS_TITLE_COL`, `NEWS_BODY_COL`.
- `combine_headline_body(title, body)` склеивает в `"{title}. {body}"`.
- `clean_news_text` снимает HTML-теги (`<[^>]+>`), `html.unescape`, схлопывает пробелы.

При `NEWS_POST_PARSE_OZON_FILTER=True` строки оставляются, если в `title` или `text` есть подстрока из `OZON_KEYWORDS_LOWER` (`ozon`, `озон`, `ozon holdings`, `маркетплейс ozon`, `ozon bank`, `озон-банк`). Регистронезависимо.

**Почему фильтр после загрузки, а не на стороне источника.** Новостные API возвращают шумный поток; фильтр на парсере гарантирует, что одни и те же правила применяются к любому источнику (CSV, VK).

#### 2.5.3. NLP-инференс тональности (`news/sentiment.py`)

Если в CSV нет числовой колонки `sentiment`, вызывается `predict_sentiment_batch`:

1. **Модель**: `seara/rubert-tiny2-russian-sentiment` по умолчанию (`NEWS_MODEL`); допускается локальный путь к `save_pretrained`-каталогу.
2. **HuggingFace pipeline**: `AutoTokenizer.from_pretrained` и `AutoModelForSequenceClassification.from_pretrained` с проверкой, что у чекпоинта есть веса классификационной головы (иначе явная ошибка про базовый MLM-чекпоинт).
3. **Mitigation для macOS**: до `import torch` устанавливаются `OMP_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, `KMP_DUPLICATE_LIB_OK=TRUE`; на Darwin вызывается `torch.set_num_threads(1)` — снижает риск SIGSEGV при OpenMP-конфликтах. Если запрошен `mps`, принудительно используется `cpu`.
4. **Инференс**: батчами (`NEWS_BATCH_SIZE`), `padding=True`, `truncation=True`, `max_length=NEWS_MAX_LENGTH=512`.
5. **Скаляр тональности**: для multi-label — `sigmoid(logits)`, иначе `softmax(logits)`. Затем скаляр \(s = \text{proba} \cdot w\), где \(w_i \in \{-1, 0, +1\}\) определяется автоматически по `id2label[i]` (negative/neutral/positive). Совместимо с карточкой `cointegrated/rubert-tiny-sentiment-balanced`.

**Почему такой скаляр.** Простой и интерпретируемый: −1 при чистом негативе, +1 при чистом позитиве, 0 при балансе. Альтернатива — argmax-метка (категориальный признак) — теряет информацию о неуверенности модели и требует one-hot.

#### 2.5.4. Дневные агрегаты (`news/aggregate.py`)

Для каждого дня из `trading_index`:

- `sentiment_score` = среднее тональностей новостей этого дня; **NaN** для дней без новостей (важно: NaN ≠ нейтральная тональность 0).
- `news_count` = число новостей в день; в дни без новостей — 0.
- `has_news = 1{news_count > 0}`.
- `sentiment_trend_3` = `rolling(3, min_periods=1).mean()` от `sentiment_score`.
- `sentiment_volatility` = `rolling(5, min_periods=1).std()` от `sentiment_score`.

**Почему именно такие фичи.** `sentiment_score` — уровень настроения, `sentiment_trend_3` — краткосрочная инерция, `sentiment_volatility` — нестабильность настроения (расходящиеся новости часто предшествуют скачкам цены), `news_count`/`has_news` — просто фактор внимания рынка.

#### 2.5.5. Слияние с котировками (`news/merge.py`)

Колонки добавляются в `df_feat` по торговому индексу. При отсутствии файла или флага возвращается `_ensure_zero_news_features` — нули в счётчиках и NaN в тональности (далее обрабатываются билдером).

### 2.6. Сборка X и таргетов (`features/builder.py`)

#### 2.6.1. Состав признаков

```python

cols.extend(f"log_ret_lag{k}" for k in range(1, n_lags + 1))

```

`FEATURE_COLS` — фиксированный список из 29 имён ТА/HAR/календарных признаков. Лаги `log_ret_lag*` добавляются по `N_LAGS`. При новостях добавляются 5 фич.

#### 2.6.2. Импутация и dropna

```python
drop_subset = [c for c in available if c not in NEWS_SENTIMENT_NAN_OK]
feat = feat.dropna(subset=drop_subset)
```

- Строки с NaN по **техническим** и **счётчиковым** признакам **удаляются** — это NaN из rolling-индикаторов на старте ряда, их нельзя осмысленно заполнить.
- Для `sentiment_score`/`sentiment_trend_3`/`sentiment_volatility` NaN допустимы и **импутируются медианой по дням с новостями** (`feat.loc[feat["has_news"] > 0, col].median()`); fallback — 0.

**Почему медиана по дням с новостями, а не 0.** Заполнение нулём смешало бы «нет новости» с «нейтральная новость», что искажает распределение признака. Медиана сохраняет «типовой уровень тональности» и не вносит выбросов. Глобальное среднее было бы менее устойчивым к редким экстремально-негативным дням (например, шок 24.02.2022).

#### 2.6.3. Таргеты (multi-horizon, direct multi-step)

```python
tgt[f"reg_{h}"] = log_ret.rolling(int(h)).sum().shift(-int(h))
tgt[f"clf_{h}"] = (tgt[f"reg_{h}"] > 0).astype(int)
```

Для каждого \(t\): `reg_h(t) = sum(r[t+1..t+h])` — кумулятивная лог-доходность за \(h\) следующих дней (аддитивное свойство логов). `clf_h(t) = 1{reg_h > 0}`.

**Почему direct multi-step, а не recursive (рекурсивная h-шаговая прогонка одношаговой модели).** Рекурсивный подход накапливает ошибку с шагом; direct обучает отдельную модель на каждый горизонт, что на коротких горизонтах эмпирически точнее и не зависит от качества промежуточных прогнозов.

#### 2.6.4. Выравнивание X и таргетов (`pipeline._prepare_targets_and_features`)

```python
data = X.join(tg, how="inner").dropna()
```

Удаляются последние `max(h)` строк (где будущее недоступно) и любые строки с NaN. Возвращаются `X_aligned`, `tg_aligned` с общим индексом.

**Создаётся.** `X_aligned` — матрица признаков (`N × p`), `tg_aligned` — все колонки `reg_h`, `clf_h`. Передаются в `walk_forward_train_eval` для каждого \(h\).

### 2.7. Опциональная винзоризация и масштабирование (`models/scaling.py`)

#### 2.7.1. Винзоризация

При `WINSORIZE_OUTLIERS=True`:

```python
lo = np.nanpercentile(arr_train, 5)
hi = np.nanpercentile(arr_train, 95)
X_tr[col] = X_tr[col].clip(lower=lo, upper=hi)
X_te[col] = X_te[col].clip(lower=lo, upper=hi)  # те же границы из train
```

Границы оцениваются **только по train**, затем применяются к train и test. Это сохраняет временную чистоту валидации (никакой информации из test в подготовке данных не утекает).

**Почему винзоризация, а не удаление выбросов.** Удаление строк меняет временную ось и порядок, что неприемлемо для walk-forward. Клиппинг сохраняет порядок и количество строк, ограничивая лишь экстремальные значения отдельных признаков. Особенно важно для **Ridge**, у которого квадратичная функция потерь даёт большим значениям непропорциональный вес.

**Почему квантили 5/95, а не 1/99 или 10/90.** 5/95 — сбалансированный компромисс: режутся редкие экстремумы (~10% хвостов в сумме), не теряется информация о повседневной волатильности.

**По умолчанию выключено** (`WINSORIZE_OUTLIERS=False`): режим RobustScaler уже даёт устойчивость к хвостам. Включается, если эксперимент покажет, что Ridge нестабилен.

#### 2.7.2. RobustScaler

```python
scaler = RobustScaler(quantile_range=(10, 90)).fit(X_tr_in)
```

`RobustScaler` центрирует по медиане и масштабирует на интерквантильный размах (по умолчанию 25–75; здесь шире — 10–90). На каждом WF-фолде scaler **обучается заново** на train и применяется к train и test.

**Почему RobustScaler, а не StandardScaler/MinMaxScaler.**
- Тяжёлые хвосты лог-доходностей и `OBV_z` делают `mean`/`std` нестабильными → StandardScaler искажается.
- MinMaxScaler чувствителен к одной точке-экстремуму (она становится 1.0, всё остальное сжато в узком диапазоне).
- RobustScaler по медиане и квантилям даёт устойчивые статистики; квантили 10/90 ещё больше «отрезают» хвосты от оценки шкалы по сравнению со стандартным 25/75.

**Почему именно train→test, а не глобально.** Глобальный fit на всём ряде утечёт статистики теста в обучение → завышенная оценка качества. Pure train-fit — стандарт предотвращения leakage в финансовом ML.

**Создаётся.** `Xs_tr`, `Xs_te` — масштабированные `DataFrame` с теми же индексами и именами колонок, что и оригиналы. Используются в `_fit_regressors_on_fold`/`_fit_classifiers_on_fold` и в `fit_stacking`.

### 2.8. Разбиение данных: walk-forward с purging и embargo (`models/walk_forward._purged_splits`)

```python
total_test = max(1, int(n * float(test_fraction)))   # TEST_FRACTION=0.2
test_size = max(1, total_test // n_splits)            # WF_SPLITS=10
for i in range(n_splits):
    test_end   = n - (n_splits - 1 - i) * test_size
    test_start = test_end - test_size + embargo       # EMBARGO_DAYS=10
    train_end  = test_start - embargo
    train_start= max(0, train_end - train_window)     # TRAIN_WINDOW=504
```

#### Параметры по умолчанию

- `WF_SPLITS=10` — 10 последовательных фолдов.
- `TEST_FRACTION=0.2` — суммарно 20% хвоста делятся на 10 окон.
- `TRAIN_WINDOW=504` — ~2 торговых года истории.
- `EMBARGO_DAYS=10` — зазор между концом train и началом test.

**Почему walk-forward, а не K-Fold.** K-Fold перемешивает наблюдения и допускает обучение на «будущем» относительно теста. На временных рядах это утечка. WF имитирует реальный процесс: «обучили на прошлом → предсказали следующий блок → сдвинули окно».

**Почему purging + embargo.** Целевая переменная `reg_h` — кумулятивная сумма следующих \(h\) дней; значения `reg_h(t)` и `reg_h(t+1)` пересекаются по информации о \(r_{t+1}\). Без зазора последние \(h-1\) точек train «смотрят» в test → утечка. Embargo физически отделяет окна.

**Почему фиксированное `TRAIN_WINDOW`, а не expanding window.** На длинных рядах expanding window закрепляет модель в старых режимах рынка; sliding window держит «свежий» контекст. 504 дня выбраны как компромисс между статистической мощью и адаптивностью.

**Создаются.** Пары `(tr_idx, te_idx)` индексов numpy для каждого фолда; используются `X.iloc[tr_idx]`, `X.iloc[te_idx]` и аналогично для `y_reg`, `y_clf`.

### 2.9. Веса наблюдений (`_crisis_sample_weights`)

```python
crisis = X_tr.get("in_crisis", pd.Series(0, index=X_tr.index))
return np.where(crisis == 1, 0.3, 1.0)
```

Все 2022 (с 24.02 по 31.12) получают вес 0.3, остальные — 1.0. Передаются в `RFreg.fit`, `RFclf.fit`, `LGBreg.fit`, `LGBclf.fit` через `sample_weight`. Ridge `sample_weight` не получает (не реализовано в текущем коде).

**Почему так.** 2022 — структурный шок (приостановка торгов, санкции, делистинг GDR), статистические зависимости отличаются. Полное удаление этих дней разорвало бы временной ряд; полный вес — модель «зацепится» за нерепрезентативный режим. Понижение веса до 0.3 — компромисс: данные используются, но влияние ограничено.

### 2.10. Модели машинного обучения

#### 2.10.1. Ridge (регрессия)

**Постановка.** \(\hat{\beta} = \arg\min_\beta \|y - X\beta\|_2^2 + \alpha \|\beta\|_2^2\). Аналитическое решение: \(\hat{\beta} = (X^\top X + \alpha I)^{-1} X^\top y\); sklearn использует SVD/Cholesky.

**Гиперпараметры.** `RIDGE_ALPHA=1.0`. Регуляризация по умолчанию — стандартное значение, на котором при `RobustScaler(10, 90)` коэффициенты получаются «мягкими».

**Почему Ridge.**
- Базовый линейный бенчмарк, обязательный для финансовых задач.
- Устойчив к мультиколлинеарности (RSI, Stoch, MACD, BB сильно коррелированы).
- Интерпретируемость направления эффекта.
- Быстрый: переобучается на каждом фолде за миллисекунды.

**Альтернативы.** OLS — нестабилен при мультиколлинеарности. Lasso — отбирал бы признаки, но коррелированные ТА-признаки часто заменяют друг друга, и единственный «выживший» лассо-коэффициент даёт нерепрезентативную интерпретацию. ElasticNet — компромисс, не используется (можно добавить).

#### 2.10.2. Random Forest (Regressor и Classifier)

**Алгоритм.** Ансамбль `n_estimators` деревьев CART, обученных на бутстреп-выборках; в каждой вершине рассматривается случайное подмножество признаков (по умолчанию `sqrt(p)` для классификации, `p/3` для регрессии). Прогноз — среднее (регрессия) или мажоритарное голосование/средняя вероятность (классификация).

**Гиперпараметры.**

| Параметр | Регрессия | Классификация | Зачем |
|---|---|---|---|
| `n_estimators` | 200 | 200 | Стабильность ансамбля. |
| `max_depth` | 6 | 5 | Регуляризация против переобучения на шумных доходностях. |
| `min_samples_leaf` | 5 | 5 | Минимум 5 наблюдений на лист → защита от подгонки под единичные шумы. |

**Почему ограничения по глубине и листу.** На дневных данных без ограничений RF быстро строит деревья глубиной 20+, выучивающие индивидуальные «торговые сессии», и теряет обобщающую способность.

**Почему RF, а не gradient boosting в одиночку.** RF и LGB по-разному ловят сигнал: RF — averaging некоррелированных предикторов, LGB — sequential boosting. Их совмещение в стекинге даёт diversity.

#### 2.10.3. LightGBM (Regressor и Classifier)

**Алгоритм.** Гистограммный градиентный бустинг с leaf-wise ростом дерева (выбирается лист с максимальным приростом потерь). Поддерживает регуляризацию через `num_leaves`, `min_child_samples`, `subsample`, `colsample_bytree`.

**Гиперпараметры (для регрессии).**

| Параметр | Значение | Логика |
|---|---|---|
| `n_estimators` | 300 | Достаточно для конвергенции при `lr=0.05`. |
| `learning_rate` | 0.05 | Стандартный компромисс точность/время. |
| `num_leaves` | 31 | Стандарт LGB; контролирует сложность деревьев. |
| `max_depth` | -1 | Неограниченная глубина (контролируется через `num_leaves`). |
| `min_child_samples` | 20 | Минимум 20 точек в листе. |
| `subsample` | 0.8 | Bagging: 80% строк на каждое дерево → diversity и регуляризация. |
| `colsample_bytree` | 0.8 | Случайные 80% признаков на каждое дерево. |

Параметры классификатора могут быть переопределены ключами `LGBCLF_*`; при `None` берутся значения регрессора (унификация настроек).

**Почему LGB.** Сильнейшая модель на табличных данных по большинству бенчмарков; быстрее XGBoost за счёт гистограмм и leaf-wise роста.

#### 2.10.4. Подбор гиперпараметров

В коде **нет автоматического подбора** (Grid/Random Search, Optuna, Hyperopt). Все гиперпараметры заданы статически в `CFG`. Подбор сводится к ручной правке `config.py` и повторному прогону `run_experiment` с последующим сравнением метрик.

**Почему так.** Для ВКР важна **воспроизводимость** и фиксированная конфигурация для отчёта; автотюнинг в WF-режиме на ограниченном объёме данных склонен к переобучению на split-структуре. При желании можно обернуть `walk_forward_train_eval` в Optuna-цикл, передавая разные `cfg`.

#### 2.10.5. Цикл обучения на фолде

Для каждого `(tr_idx, te_idx)` (всего `WF_SPLITS=10`):

1. Срезы `X_tr/X_te`, `y_r_tr/y_r_te`, `y_c_tr/y_c_te`.
2. Винзоризация (если включена) и `RobustScaler` train→test.
3. Sample weights по кризису.
4. **Регрессоры**: `Ridge.fit(Xs_tr, y_r_tr)` и `RF/LGB.fit(Xs_tr, y_r_tr, sample_weight=sample_w)`. Прогнозы записываются в `fold_preds["pred_<Name>"]`, метрики — в `res_reg`.
5. **Классификаторы**: `RFclf/LGBclf.fit(...)`, `predict_proba` для AUC. Метрики — в `res_clf`.
6. После всех фолдов `pd.concat(all_preds).sort_index()` даёт сквозной `preds_df` и **диагностику остатков** (`validate_residuals`: Ljung-Box и ADF) для каждого регрессора.

### 2.11. ARIMA + GARCH (`pipeline.run_hybrid_arima_garch`, `models/walk_forward.rolling_forecast_hybrid_arima_garch`)

#### 2.11.1. Постановка

- **Уравнение среднего**: ARIMA(p,d,q) с `ARIMA_ORDER=[1, 0, 1]` (по умолчанию). Поскольку входной ряд — лог-доходности (уже стационарные), `d=0` — обоснованное допущение; ADF в EDA эту гипотезу проверяет.
- **Уравнение дисперсии (только для h=1)**: GARCH(p, q) на in-sample остатках ARIMA, `mean="Zero"`, `GARCH_P=GARCH_Q=1`.

#### 2.11.2. Прогноз для h=1

```python
arima_res = ARIMA(y_history, order=arima_order).fit()
fc = arima_res.get_forecast(steps=1)
mu_hat = float(fc.predicted_mean.iloc[0])
# на остатках ARIMA — GARCH
eps_scaled = arima_res.resid.dropna().values * 100
garch_res = arch_model(eps_scaled, mean="Zero", vol="GARCH", p, q, rescale=False).fit()
sigma2_hat = garch_res.forecast(horizon=1).variance.values[-1, 0] / 10000
half_width = norm.ppf(1 - alpha/2) * sqrt(sigma2_hat)
ci = (mu_hat - half_width, mu_hat + half_width)
```

При сбое GARCH (мало остатков, не сходится) — **fallback** на ДИ из statsmodels ARIMA. Масштабирование ε×100 — стандартный приём для численной устойчивости в `arch`.

**Почему гибрид, а не чистая ARIMA.** ARIMA даёт гомоскедастичный ДИ (одинаковую ширину на всём периоде), что неадекватно для финансовых рядов с volatility clustering. GARCH моделирует условную дисперсию и даёт **адаптивные** ДИ: широкие в волатильные периоды, узкие в спокойные.

**Почему именно ARIMA(1,0,1) и GARCH(1,1).** Это «канонические» порядки для финансовых рядов (Box–Jenkins, Bollerslev). Они обычно описывают данные не хуже более сложных при минимуме параметров.

#### 2.11.3. Прогноз для h>1

```python
fc = ARIMA(y_history, order=arima_order).fit().get_forecast(steps=max_h)
mu_h = float(fc.predicted_mean[:h].sum())  # кумулятивный прогноз
ci_lo_h = float(fc.conf_int(alpha)[:h, 0].sum())
ci_hi_h = float(fc.conf_int(alpha)[:h, 1].sum())
```

Сумма пошаговых ARIMA-прогнозов; границы ДИ просто складываются (приближение, точная совместная область требует ковариаций).

**Почему так.** Постановка совпадает с ML-таргетом `reg_h` — это даёт корректное сравнение метрик ARIMA vs ML на одном горизонте.

#### 2.11.4. Rolling

Expanding-window: `train_end = n - test_size`, на каждом шаге `step` обучение на `y_history = y[: train_end + step]`, прогноз на следующий день и/или h дней. `test_size` определяется в `_arima_rolling_test_size`: `test_fraction × n` с минимумом 30 и ограничениями `ARIMA_GARCH_MIN_TRAIN`, `ARIMA_MAX_TEST_DAYS`.

**Создаётся.** `forecast_df` с колонками `y_realized`, `mu_forecast`, `ci_lower`, `ci_upper` (для h=1) и `*_h{h}` для остальных. Сохраняется CSV `arima_horizons_metrics.csv`, JSON `arima_best_horizon.json` (выбор лучшего h по `ARIMA_BEST_HORIZON_METRIC` или `BEST_MODEL_METRIC`), PNG `fig_forecast_arima_garch_best.png`.

### 2.12. Стекинг (`models/stacking.fit_stacking`)

#### 2.12.1. Hold-out split (`pipeline._holdout_split`)

```python
split_point = max(1, min(int(n * (1 - test_frac)), n - 1))
return X[:split_point], X[split_point:], y[:split_point], y[split_point:]
```

Последние `TEST_FRACTION=0.2` всего ряда — финальный тест стекинга, остальное — train.

#### 2.12.2. Двухуровневая схема

1. **Масштабирование**: `robust_scale_train_test(X_train, X_test, winsorize=cfg["WINSORIZE_OUTLIERS"])`.
2. **Базовые модели** обучаются на первых 80% масштабированного train: `RandomForestRegressor` и `LGBMRegressor` (параметры из `CFG`).
3. **Мета-обучение**: на оставшихся 20% train считаются предсказания базовых моделей → матрица `[N×2]`. На ней обучается `Ridge(alpha=RIDGE_ALPHA)`.
4. **Финальный прогноз**: предсказания базовых моделей на `X_test` подаются в мета-Ridge.

**Почему 80/20 внутри train.** Мета-модель должна обучаться на out-of-sample предсказаниях базовых, иначе мета-уровень переобучится на in-sample. 80/20 — компромисс: базовые модели не теряют слишком много данных.

**Почему мета-Ridge, а не более сложная мета-модель.** Признаков всего 2 (RF, LGB). Линейная комбинация с L2 — оптимальна по принципу Оккама: больше параметров не нужно, риск переобучения минимален.

**Ограничения** (зафиксированы в docstring модуля):
- Линейность мета-уровня → не ловит сложные взаимодействия RF и LGB.
- Single-fold split: при смене режима рынка веса мета-модели устаревают.
- Нет CV-блендинга (как у `sklearn.ensemble.StackingRegressor`); упрощено намеренно.

**Создаётся.** Словарь метрик регрессии под меткой `Stacking(RF+LGB)`, сохраняется в `stacking_h{h}.csv` и в общую `stacking_summary.csv`.

### 2.13. Метрики и валидация (`evaluation/metrics.py`)

#### 2.13.1. Регрессия

- **MAE** = \(\frac{1}{N}\sum |y - \hat{y}|\).
- **RMSE** = \(\sqrt{\frac{1}{N}\sum (y - \hat{y})^2}\).
- **MAPE** (с `eps=1e-8`): чувствителен к близким к нулю фактическим значениям → в комментарии предупреждение.
- **R²** — через ручную формулу с `eps` в знаменателе для устойчивости.
- **MDA** (Mean Directional Accuracy, %) — доля совпадений знака. Для трейдинга часто важнее RMSE.
- **Spearman IC** и p-value: ранговая корреляция факта и прогноза. Стандартная метрика «силы сигнала» в количественных финансах.

**Почему такой набор.** Покрывает три аспекта качества:
- абсолютная точность (MAE/RMSE),
- объяснённая дисперсия (R²),
- торговая полезность (MDA, IC).

#### 2.13.2. Классификация

- **Accuracy**, **F1** (`zero_division=0`), **ROC-AUC** (NaN при недопустимых данных).

#### 2.13.3. Торговые метрики

```python
strat_ret = y_true_ret * y_pred_direction - |Δposition| * commission
cum = exp(cumsum(strat_ret))
annual_ret = (cum[-1] ** (252/n) - 1) * 100
sharpe   = mean / std * sqrt(252)
sortino  = mean / std_neg * sqrt(252)
max_dd   = min((cum - running_max) / running_max) * 100
calmar   = annual_ret / |max_dd|
```

`COMMISSION=0.0005` (0.05%) на смену позиции. Sharpe/Sortino аннуализированы множителем \(\sqrt{252}\) (число торговых дней).

**Почему long/short по знаку.** Простейшая интерпретируемая стратегия для оценки экономической ценности классификатора. Даёт ответ: «если бы инвестор открывал позицию по знаку лучшего классификатора каждый день — какие были бы Sharpe/просадки?»

#### 2.13.4. Buy & Hold (бенчмарк)

Та же траектория `y_true_ret`, но с фиксированной long-позицией: годовая доходность, Sharpe, Calmar, MaxDD. Используется как «нулевой» бенчмарк.

#### 2.13.5. Naive(0)

Прогноз `y_pred = 0` для регрессии. Это «наивный» бенчмарк: если RMSE модели ≥ RMSE Naive(0), модель **не превосходит** игнорирование признаков.

#### 2.13.6. Диагностика остатков

`validate_residuals` после WF:

- **Ljung-Box** на лагах 10 и 20: \(H_0\) — остатки белый шум; p > 0.05 — структура исчерпана. Если автокорреляция остаётся, в логах warning.
- **ADF** на стационарность остатков: p < 0.05 — стационарны.

**Зачем.** Если остатки автокоррелированы или нестационарны — модель недомоделирует ряд, есть запас для улучшения (например, добавить лаги или динамическое масштабирование).

#### 2.13.7. Выбор лучшей модели (`evaluation/wf_selection.py`)

- `mean_metrics_by_model(df_reg)` — средние метрики по фолдам отдельно по модели.
- `select_best_model(agg, metric)` — для RMSE/MAE/MAPE минимизация, для R²/Accuracy/AUC/F1 максимизация (`_maximize` set).
- `overall_best_across_horizons(per_horizon_aggs, metric)` — сначала среднее метрики по h, затем выбор.

### 2.16. ARIMA-GARCH в задачах регрессии и классификации

ARIMA(-GARCH) исторически работает на ряде лог-доходностей и решает регрессионную
постановку: оценка условного среднего \(\hat{\mu}_h(t)\) и условной дисперсии
\(\hat{\sigma}^2_{t+1\mid t}\) (только для \(h=1\)). Чтобы сравнивать его с
ML-классификаторами, в пайплайн добавлена прозрачная редукция «регрессия →
классификация» — без дообучения второй модели и без новых гиперпараметров.

#### 2.16.1. Регрессионный режим

| Что выдаёт | Где | Колонка |
|---|---|---|
| \(\hat{\mu}_1\) (гибрид ARIMA+GARCH) | `forecast_df` | `mu_forecast` |
| Кумулятивный \(\hat{\mu}_h = \sum_{k=1}^h \hat{\mu}_{t+k}\) | `forecast_df` | `mu_forecast_h{h}` |
| Гауссов 90% ДИ из \(\hat{\sigma}^2\) (h=1) или сумма границ ARIMA (h>1) | `forecast_df` | `ci_lower`, `ci_upper`, `*_h{h}` |
| Метрики регрессии (MAE/RMSE/MAPE/R²/IC) | `arima_horizons_metrics.csv` | строки `model=ARIMA_h{h}` |

Используется в графике `fig_forecast_arima_garch_best.png` и в выборе лучшего
\(h\) по метрике `ARIMA_BEST_HORIZON_METRIC`.

#### 2.16.2. Классификационный режим (новое)

Реализован двумя дополняющими функциями:

- `models.walk_forward.arima_garch_classification_from_forecasts(forecast_df, horizons)` —
  для каждого валидного \(h\):

  \[
  y^{clf}_t = \mathbf{1}[r_h(t) > 0], \quad
  \hat{y}^{clf}_t = \mathbf{1}[\hat{\mu}_h(t) > 0], \quad
  \text{score} = \hat{\mu}_h(t).
  \]

  Возвращает список словарей с `Accuracy`, `F1`, `AUC` (стандартные `sklearn.metrics`
  через `evaluation.metrics.classification_metrics`).

- `pipeline._arima_horizon_clf_metrics_df` — приводит результат к `DataFrame`
  и сохраняет в `arima_horizons_clf_metrics.csv` внутри `run_hybrid_arima_garch`.

**Почему именно знак прогноза, а не отдельная классификационная модель.**

1. **Согласованность с ML-таргетом.** `FeatureBuilder.build_targets` определяет
   `clf_h = 1{reg_h > 0}`, ровно та же редукция применяется к ARIMA-прогнозу.
   Иначе сравнение было бы методически некорректным (разные определения «победы»).
2. **Отсутствие новых гиперпараметров.** Порог 0 фиксирован: знак суммы лог-доходностей
   = направление цены за горизонт.
3. **Корректный AUC без калибровки.** ROC-AUC требует только монотонную функцию
   «уверенности». \(\hat{\mu}_h\) монотонно растёт по «шансам роста», поэтому
   `roc_auc_score(y_true, mu_forecast)` корректен без логистической прослойки.

**Где встраивается в pipeline.**

```text
run_hybrid_arima_garch(df, cfg, out)
├─ rolling_forecast_hybrid_arima_garch        # forecast_df
├─ _arima_horizon_metrics_df       → arima_horizons_metrics.csv
├─ _arima_horizon_clf_metrics_df   → arima_horizons_clf_metrics.csv   # NEW
└─ arima_best_horizon.json (regression + classification_metrics_by_horizon)
```

**Сравнение с ML-классификаторами.** В `run_ab_comparison` строится единая
сводная таблица `ab_comparison_summary.csv` со столбцом `family ∈ {ML, ARIMA-GARCH}`,
где для каждой модели и горизонта приводятся одни и те же метрики `Accuracy/F1/AUC`.
ARIMA-GARCH встаёт строкой рядом с RF/LGB на каждом \(h\); метрики ARIMA в режимах
«с новостями» и «без новостей» совпадают (новости в ряд не входят), Δ всегда ноль —
это явно отражено в столбце `improved_by_news` (False для ARIMA).

#### 2.17.1. Что именно сравнивается

`run_ab_comparison(cfg, data_path, out_dir)` запускает `run_experiment` дважды
с одинаковыми сплитами walk-forward, моделями, сидами и гиперпараметрами:

| Параметр | Baseline (no-news) | News-enhanced |
|---|---|---|
| `USE_NEWS_FEATURES` / `USE_NEWS_SENTIMENT` | `False` | `True` |
| `attach_news_sentiment_features` | возвращает `df` без новостных колонок | добавляет 5 колонок |
| `FeatureBuilder.feature_cols` | TA + календарь + лаги | + 5 новостных |
| `dropna(subset=…)` | по тем же не-новостным колонкам | по тем же не-новостным колонкам |
| WF-сплиты, embargo, train_window | те же | те же |
| Сиды (`SEED`/`RANDOM_STATE=42`) | те же | те же |
| Модели (Ridge/RF/LGB) | те же | те же |
| ARIMA-GARCH | тот же ряд `log_ret` → те же прогнозы | идентичны (новости в ряд не входят) |

**Корректность выравнивания.** Множество строк после `dropna` совпадает в обоих
прогонах, потому что новостные колонки `sentiment_*` находятся в whitelist
`NEWS_SENTIMENT_NAN_OK` и не участвуют в `dropna(subset=...)`. Признаки `news_count`/
`has_news` либо отсутствуют (baseline), либо принимают значения 0/1 без NaN
(news-enhanced) — на dropna не влияют. Длина `X` одинакова → WF выдаёт идентичные
индексы train/test → сравнение моделей честное (отличие исключительно в наборе
столбцов `X`).

#### 2.17.3. Семантика дельты

`delta_with_minus_no = with_news − no_news`. Столбец `direction` фиксирует, что
именно считать улучшением:

| Метрика | direction | Улучшение от новостей |
|---|---|---|
| MAE, RMSE, MAPE | `lower_is_better` | `delta < 0` |
| R², MDA_%, IC, Accuracy, F1, AUC | `higher_is_better` | `delta > 0` |

Столбец `improved_by_news ∈ {True, False, None}` ставит метку автоматически.
В `ab_winners_*.csv` собирается «доля моделей, у которых новости улучшили
данную метрику на данном горизонте» — это интегральный показатель полезности
новостных признаков (важнее, чем единичный прирост лучшей модели).

#### 2.17.4. Интерпретация результата

- Если **share_improved_by_news ≥ 0.66** на ключевых метриках (RMSE/AUC) на нескольких
  горизонтах — новости вносят систематический прирост; имеет смысл их включать.
- Если **share_improved_by_news ≈ 0.5** — эффект случаен, новости не дают
  устойчивого улучшения.
- Если **share_improved_by_news ≤ 0.33** — новости вредят (шум в признаках).

Это даёт ВКР количественный ответ на гипотезу «новости улучшают прогноз
доходности OZON» без зависимости от выбора одной модели.

#### 2.17.5. Где находится переключатель в коде

| Слой | Ключ/функция | Поведение |
|---|---|---|
| `config.py` | `CFG["USE_NEWS_FEATURES"]`, `CFG["USE_NEWS_SENTIMENT"]` | Канонический + legacy флаги. |
| `config.resolve_news_features_flag(cfg)` | возвращает итоговое `bool` | Используется в `news/merge.py` и `features/builder.py`. |
| `config.set_news_features_flag(cfg, value)` | согласованно проставляет оба ключа | Вызывается в `run_experiment` при подаче `use_news_features`. |
| `pipeline.run_experiment(..., use_news_features=...)` | приоритетный аргумент | None = взять из CFG; True/False = принудительно. |
| `main.py --with-news / --no-news` | флаги CLI для одиночного прогона | Mutually exclusive. |
| `main.py --ablation` или `CFG["RUN_NEWS_ABLATION"]=True` | вызвать `run_ab_comparison` | Запуск A/B. |

**Вывод по корректности.** Новостные признаки не порождают утечку:

- `news/aggregate.daily_sentiment_features` агрегирует новости по
  `pd.to_datetime(news.date).dt.normalize()` и реиндексирует на `trading_index`
  без сдвига вперёд: для дня \(t\) используются только новости с датой \(\le t\)
  (источник CSV — публикации с timestamp того же или более раннего дня).
- `dropna` в `FeatureBuilder` не подмешивает будущие значения; импутация
  `sentiment_*` идёт медианой по фолду в момент построения матрицы, до WF —
  но это не утечка таргета: импутируется только сам признак, и значение
  одинаково для train и test (одна оценка медианы по всему наблюдённому
  набору дней с новостями). Альтернатива — медиана по train в каждом фолде —
  даст ещё более строгий контроль, но эмпирически разница пренебрежима;
  при необходимости легко поднять в WF-цикл.
- ARIMA-GARCH работает на `df["log_ret"]` и не использует новости — поэтому
  его результаты должны совпадать в обоих прогонах. Это используется как
  «консистентная контрольная точка» в `ab_comparison_summary.csv`.

## 4. Воспроизводимость и запуск

```bash
python -m venv .venv
source .venv/bin/activate                  # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python main.py --smoke                     # быстрая проверка окружения (без ML/ARIMA)

# Одиночный прогон (по флагу в CFG):
python main.py
python main.py --data path/to/OZON.csv --out ./results

# Принудительные одиночные режимы:
python main.py --no-news --out ./results_baseline      # baseline без новостей
python main.py --with-news --out ./results_news        # news-enhanced

# Честный A/B эксперимент (две одинаковые WF-сессии, плюс ARIMA-GARCH):
python main.py --ablation --out ./results_ab
```

В каталоге `./results_ab` после `--ablation` появятся подкаталоги
`baseline_no_news/`, `news_enhanced/` и сводные таблицы
`ab_comparison_*.csv`, `ab_winners_*.csv`, `ab_comparison_summary.csv`,
`ab_meta.json` (см. §2.17).

Все случайные процедуры зафиксированы через `RANDOM_STATE`/`SEED` (значение 42 в `CFG`):

- `RandomForestRegressor/Classifier(random_state=seed)`,
- `LGBMRegressor/Classifier(random_state=seed)`,
- стекинг — те же seed-аргументы.

Ridge и `RobustScaler` детерминированы. ARIMA/GARCH — `statsmodels`/`arch`, тоже детерминированы при идентичных данных.

## 5. Резюме «зачем именно так»

| Этап | Метод | Альтернатива | Почему выбран этот |
|---|---|---|---|
| Загрузка CSV | перебор `,;\t`, нормализация колонок | жёсткий sep | устойчивость к разным экспортам MOEX/Excel. |
| Заполнение цен | ffill | интерполяция | сохраняет реальную последнюю цену, не «рисует» сделок. |
| Заполнение объёма | rolling(20) median | среднее, ноль | робастность к всплескам. |
| Выбросы | MAD-z + лог-warning | удаление, IQR | сохраняем реальные кризисные дни; MAD устойчив. |
| Доходность | log return | pct_change | аддитивность для cumulative-таргетов, симметрия. |
| Лаги | `N_LAGS=10` | без лагов | прямой доступ к автокорреляции для линейных моделей. |
| Объём | rolling z-score OBV (`OBV_NORM_WINDOW`) | сырой OBV | стационарность. |
| Календарь | sin/cos + бинарные | one-hot | непрерывная геометрия и компактность. |
| Импутация sentiment | медиана по дням с новостями | 0 / mean | сохраняет «типовой уровень»; не путает «нет новости» с «нейтральная». |
| Винзоризация | train-quantile clip 5/95 | удаление, no-op | не ломает временной ряд, ограничивает влияние выбросов на Ridge. |
| Масштабирование | RobustScaler(10, 90), train→test | StandardScaler/MinMax | устойчивость к хвостам, без leakage. |
| Валидация | purged WF + embargo | KFold, expanding | имитация реального переобучения, без leakage. |
| Веса | crisis 0.3 / 1.0 | удаление 2022, равные веса | не разрывает ряд, ограничивает влияние нерепрезентативного режима. |
| Регрессия | Ridge + RF + LGB | один LGB | разнообразие моделей, бенчмарк линейный↔нелинейный. |
| Классификация | RF + LGB | logreg | направление — задача с нелинейностями. |
| Стекинг | RF+LGB → Ridge | sklearn StackingRegressor | минималистичная мета-модель; CV-блендинг намеренно опущен. |
| Baseline | ARIMA(1,0,1)+GARCH(1,1) | ARIMA / Naive | адаптивные ДИ; стандарт финансовой эконометрики. |
| Метрики | MAE/RMSE/MAPE/R²/MDA/IC + Sharpe/Sortino/Calmar | только RMSE | покрытие точности и торговой полезности. |
| Подбор гиперпараметров | фиксированный CFG | Grid/Optuna | воспроизводимость для ВКР. |
